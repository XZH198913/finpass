> 回填说明：v2 有 6 条，v3 回填评审 12 条时整节丢失。1–5 为 v2 原文逐字；6 为

> 则与阶段 0 判据 8、阶段 7a 判据 4 直接冲突。

1. **不改"不承诺自动得到正确答案"的边界**：自动决策只执行 profile 显式声明的目标态，其余一律 `flagged_kept`。理由：团队意图明确要求边界不变。
2. **不改哈希算法与 verify 判据**；profile schema 升级导致的 `profile_version` 变更属 schema 演进的正常部分，但护照必须同时带 `profile_schema_version` 与 `profile_version`，使 verify 能区分"算法未变但 schema 升级"与"算法变了"。理由：v1 把两者混为一条，与 Q2 的 schema 升级冲突。
3. **不解决工程基建缺口**（无 git 仓库、无 CI 配置，J）。
4. **不补 `fund_nav` 域内容**（J：40 字节 TODO）。
5. **不删除 interactive 通道**，只由 Q8 决定其时序。
6. **除阶段 0 判据 2 兼容表已登记的报错行外，旧产物兼容只允许 warn 与跳过，不新增报错路径**（G4 现四项判据不校验字段集合）。
   **唯一例外** `[新增段落]`：`passport_id` 缺失且被当作 patch 父代引用时，必须报错，不得补发 id。依据：阶段 0 判据 8、阶段 7a 判据 4。
   （错误消息与提示文案以判据 8 为准，本节不复述，避免两处漂移。）

   > 例外为何成立：warn 的语义是「残留但结果仍可信」。缺 `passport_id` 的护照作父代时，
   > 父代产物集合与 `parent_clean_sha256` 都没有比对基准，`ext:patch_parent` 的齐备性判据
   > 失去锚点，产出的补丁无法被 verify 验证——属于结果不可信，不是轻微降级。
   > 「不得补发 id」是关键：补发会让新旧产物在链上不可区分，等于绕开例外本身。

## 阶段清单

### 阶段 0：验收口径先行

**入口**：v2 已拍板三条在案；侦察报告 A~J 为唯一事实源；评审 1、4 的裁决方向在案。
**出口**：五份登记物落地，且**表本身可被测试解析**。

**验收判据（可执行）**
1. **机制覆盖度表**：以"README 表格 + 一个可解析该表的测试文件"形式存在；行覆盖 H 节 6 类 `rule_type` × E 节 3 个 profile，每格状态非空且与 profile 声明一致。
   > **表格格式契约（矩阵形态）** `[新增段落·缺口 1]`：
   > 表头**恰好**为 `rule_type | <profile1> | <profile2> | <profile3> | 总状态`，中间三列必须是真实 profile 名（不写死顺序，解析时按名字匹配）；
   > 格值**四值**：`完整` / `部分` / `未做` / `N/A`（`N/A` = 该 profile 不适用此 `rule_type`）；
   > `总状态` 按**短板原则**聚合、忽略 `N/A`：有 `未做` 取 `未做`，否则有 `部分` 取 `部分`，否则 `完整`；三格全 `N/A` 取 `N/A`；
   > 解析器返回 `dict[str, dict[str, str]]`：`{rule_type: {profile: status, "总状态": status}}`；
   > 锚点固定 `## 机制覆盖度`，行序不固定（解析后按 `rule_type` 聚合）；未知格值、缺列、锚点缺失**一律抛错**，不许跳过。
   > 落地证据：`tests/test_capability_map.py`（含「文档 == profile 声明」交叉断言，改表不改 profile 会红）。
   > **未来扩值条件**：当引擎出现「某 `rule_type` 尚未实现」的情况时，值域扩为五值并新增 `缺失`（引擎无此类型）；届时同步改本判据契约 + `test_capability_map.py` 断言 + 已有行的归类。当前 6 类都已实现，故维持四值，`未做` 专指「引擎有、profile 未声明」。
2. **旧产物兼容表**：`FIELD_COMPAT` 4 行 + `SCENARIO_COMPAT` 2 行，共 6 行，**两类各自事实源**——字段四行：旧护照缺 `output_file_sha256`（warn，G4 现状）、缺 `profile_schema_version`（warn）、缺 `passport_id` 且被当父代（**报错**，评审 4）、旧 events 缺 `phase`（**跳过**，视为 `phase=initial`）；场景两行：dry-run 产物（走扩展点 `ext:dry_run`）、`auto_only` 退出码分支（登记行为变化，卡点 4）。
   > `[回填·项 5]` 第 4 分句原为「（warn/跳过）」未定死；按本项裁决固定为「跳过，视为 `phase=initial`」。
   > **phase 默认值单一来源** `[新增段落·缺口 3]`：`phase` 默认值是 `initial`，**唯一来源在本判据**；阶段 5 判据 4 及本文件其他位置一律引用本判据编号，不复述具体值。
   > **兼容表存在形式（拆两常量）** `[新增段落·缺口 2]`：`src/finpass/passport_compat.py` 承载两个常量，各自是事实源，spec 与代码不一致时以代码为准。
   > `FIELD_COMPAT`（4 键，字段 → 三值，值域 `{warn, skip, error}`）：`output_file_sha256` / `profile_schema_version` / `passport_id` / `events.phase`。
   > `SCENARIO_COMPAT`（2 键，场景 → 识别行为，值不枚举）：`dry_run` → `ext:dry_run`、`auto_only` → 退出码口径。
   > `passport_id` 的 `error` **只在被当作 patch 父代时生效**，其余场景按「字段缺失」处理——该语义属规则、不进字典值，见判据 8。
   > 断言：`FIELD_COMPAT` 键集 == 4 字段且值 ∈ 三值；`SCENARIO_COMPAT` 键集 == 2 场景且值非空；两者合计 6 行。不合并成单字典、不加 `field:` / `scenario:` 前缀（一种值类型两种语义会让断言退化成「值是 str」）。
   > **`skip` 的语义（写死）**：`skip` = 「不改写字段，下游按自身默认值处理缺失」。对 `events.phase` 而言，读端看到缺 `phase` 时按 `PHASE_DEFAULT`（= `initial`）视为 `initial`；**写入端不主动补** `initial`。写入端不动旧产物（对审计无损），读端补（下游语义统一），两者不可混为一谈。
   > 早期草案曾把值写成 `skip_initial` 表达同一意图，已废弃：把默认值编进枚举值，等于让字典承担 `PHASE_DEFAULT` 的职责，`PHASE_DEFAULT` 一改就留下历史特例值。
   > 阶段 5 判据 4 按「引用不复述」处理，见「待落地补丁 P2」。

   - **`N` 的语义**：含 `run` 在内的**总代数**。`N=5` 即 `run + 4 个 patch`；`N=2` 即 `run + 1 个 patch`。
   - **默认值 `keep_chain = 5`**。取 5 的理由：`run + 4 patch` 已覆盖绝大多数 patch 场景；
     超过 5 代说明清洗逻辑有根本问题，应重跑而不是继续 patch。
   - **允许范围 `2 ≤ N ≤ 100`**：`--keep-chain N` 覆盖默认值。
   - **越界一律拒绝**：`N < 2`（含 0、1、负数）拒绝，错误消息写明「至少 2（run + 1 patch）」；
     `N > 100` 拒绝，错误消息写明硬上限原因（产物目录无界增长违反可审计性）。

     本阶段不引入任何 passport 新字段。

     保留策略测试，缺一不合并（避免出现「改了没测」）。
   - **本判据是 `keep_chain` 数值语义的唯一事实源**：其他阶段只引用本项，不重新定义。
   - **`validate_keep_chain` 在阶段 0 是纯登记、无调用方**：接线是 7a 的交付物。7a 之前代码里出现
     「函数存在但没人调用」不是缺陷，**不许顺手接上**——提前接会绕过 7a 对「到上限后如何继续」的设计。
